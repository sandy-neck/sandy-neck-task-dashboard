> **North Star:** The SNP 500 is not a weather score. It is a beach decision engine.

---

## What this is

A 0–100 daily score answering one question: *is today a Sandy Neck day — and if so, when and how
should I enjoy it?* It converts weather, tide, wind, insects, beach access and sunset/bonfire
opportunity into a score, a plain-English explanation, and a recommended visit window.

It scores **the quality and usability of a Sandy Neck beach day**, not meteorological pleasantness
in the abstract. A day that looks "sunny and 76" can still be a poor Sandy Neck day if wind, bugs,
timing or access are wrong.

Customer surface is a Shopify widget. Long term it feeds CapeCodGPT, which consumes the score —
it does not invent it.

## Score bands

| Score | Label | Meaning |
|---|---|---|
| 90–100 | Exceptional | Rare, highly favorable |
| 80–89 | Great | Very good, limited compromises |
| 70–79 | Good | Worth going; one or two tradeoffs |
| 60–69 | Mixed | Enjoyable if timing/activity fits |
| 45–59 | Marginal | Significant compromises |
| 0–44 | Poor | Generally unfavorable |

**90+ must stay special.** If an ordinary pleasant summer day routinely scores 95, the scale has
lost its information.

## Category weights

```
base  = .25*weather + .15*wind + .20*tide + .20*beach + .10*day_extension + .10*experience
final = clamp(round(base + bonuses - penalties), 0, 100)
```

Weather splits Temperature 40% / Precipitation 35% / Cloud-sun 15% / Dew point 10%.
Beach conditions split Bugs 55% / ORV-access 25% / Other local 20%.
Bonuses cap at +8; ordinary penalties at −20.

## Embedded product decisions

- **Low tide 2:30–4:30 PM is privileged** (scores 100). It creates the broad lunch-to-dinner
  experience: outgoing tide, exposed beach at low, incoming water after.
- Sunset/bonfire is positive but secondary.
- Explanations must be grounded in **actual scoring contributions** — never generated independently.
  `contribution = weight × (factor_score − neutral)`.
- Confidence is separate from quality: `.50*freshness + .30*completeness + .20*source_reliability`.
- Override precedence: official closure > SNP manual override > fresh API > fallback > cached.
- **Commercial considerations must never modify the score.** Paid placement lives downstream.

## The convergence worth noting

While redesigning the daily analytics email on 2026-08-08 — before seeing this PRD — a crude
`beach_score` was built into `weather_client.py` to weather-adjust sales comparisons. It is a rough
subset of this engine: temperature, sun, precipitation, wind, no tide, no bugs, no interactions.

**These should be one engine, not two.** The PRD already says so: *"One environmental model can
support future profiles."* The SNP 500 is the properly specified version, so internal analytics
should consume it rather than maintain a parallel approximation.

This makes the SNP 500 dual-purpose:
1. **Customer-facing** — the widget, the product as specified.
2. **Internal denominator** — the thing that makes "was yesterday good?" answerable. Revenue against
   beach quality is the comparison that was missing on 2026-08-07, when a $1,468 day looked strong
   on the numbers and was actually a slight underperformance for the conditions.

Purpose 2 costs nothing extra once the engine exists, and it means the scoring gets exercised and
sanity-checked daily against real sales rather than sitting untested until launch.

## Deviation from the PRD, and why

The PRD specifies **Google Sheets** as the MVP computation layer. This implementation is Python
instead, which the PRD explicitly anticipates: *"Google Sheets is an MVP computation layer, not the
permanent product boundary."*

Reasons: the daily analytics agent already runs on GitHub Actions and already pulls weather and
tides, so ingestion is built. FR-01 (reproducible scoring), FR-09 (malformed payload cannot publish)
and the Appendix C golden-day suite are straightforward in Python and painful in Sheets. Config
lives in one dict, so weights and thresholds stay tunable by a non-engineer without touching logic.

The published payload matches the PRD schema exactly, so the Shopify widget contract is unchanged.

**If Sheets is preferred for hand-tuning, say so** — the config block ports over directly and the
factor tables are the same numbers.
